\chapter{Requirements}
\label{ch:requirements}
With the new workflow engine being a brand new microservice, there are not a lot of pre-existing requirements. The decision was made to not build upon the existing workflow system, but build a new one from scratch. This provides a lot of freedom in terms of technology choices, without requirements imposed by the legacy system or other components. As a result, they can choose the technologies best suited to the project, including the language in which clients would write extensions.

At the time of writing this thesis, the project is still in a preliminary brainstorming phase at TrustBuilder, and not much is known about the intended final design of the new workflow engine. However, a few goals are already set:

\begin{itemize}
    \item The workflow engine must run as a separate microservice
    \item Clients should be able to use a low-code workflow system without requiring specific programming knowledge
    \item Developers should be able to to write custom code for bespoke integrations that can be called from a low-code workflow
\end{itemize}

As seen in comparable services as part of the literature review, such a system typically consists of ``Actions'': blocks of functionality that receive inputs and produce outputs, arranged sequentially as part of a workflow. A workflow can be designed without programming knowledge, simply by placing existing Actions in the desired order and configuring them. An Action, on the other hand, consists of a distinct unit of code which can accept an input and produce an output. TrustBuilder's take on this is not yet finalized, so this hypothesis cannot be blindly followed as a target architecture, but it can serve as valuable context throughout the course of this thesis.

The goals listed earlier do not place a lot of constraints and requirements on the eventual language choice, but based on the information gathered in the literature review and the presumed eventual functionality, some key aspects can be identified.


\section{Popularity}
As it should be possible for customers to write their own extensions to the IAM platform, the popularity of the language in which these should be written is of great importance. Customers should be able to easily find a developer who can write in the chosen language. As discussed in the literature review, the most popular server-side programming languages are as follows:
\begin{itemize}
    \item JavaScript
    \item Python
    \item Java
    \item TypeScript
    \item C++
    \item C\#
    \item C
    \item PHP
    \item Go
    \item Kotlin
    \item Rust
\end{itemize}

This list serves as the long list mentioned in the methodology chapter.

\section{Memory Safety}
As mentioned in the literature review, memory safety issues are an extremely common cause for security vulnerabilities. This would make it absolutely irresponsible to use a language that is not memory-safe in an environment so specifically built around cybersecurity. This decisively rules out C and C++ as possible options.

\section{Static Types}
The literature review has shown that statically typed languages exhibit many advantages relevant to the extension system. They help prevent bugs, help fix them more quickly, and also serve as implicit documentation.

In the current system, using JavaScript, this lack of implicit documentation is clearly felt. Knowing the structure of the input received from a workflow and its expected output requires looking up external documentation. A statically typed language could be of great help here, and would make writing custom extensions more accessible to customers.

\section{Performance}
Considering these actions will be executed in response to network calls, and will typically make network calls (such as database queries and HTTP requests) themselves, the performance impact of the programming language choice will be negligible compared to the time the network calls take up. For this reason, performance is not a relevant requirement in this specific case.

\section{Testability}
Because of the outdated infrastructure around the current workflow system, testing them is no easy feat. In the next generation of workflows, the possibility to write unit tests will be of great importance. As such, the language's ecosystem should provide a reliable testing library. This can be assumed to be the case for most popular programming languages however, and will further be explored in the proof of concept.

With TypeScript and Java being the two languages currently used internally at TrustBuilder, this selection is especially interesting, as this means the necessary expertise in these languages will already present at the company.
