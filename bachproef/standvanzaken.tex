To gain a deeper understanding of the research problem and the context in which it exists, this chapter explores the technologies involved, the current state of programming language popularity, and the approaches taken by comparable services.

\section{IAM standards}
To attain further insight in the problem space, it is important to briefly discuss the dominant IAM standards. According to \textcite{Naik2016}, the most established identity protocols in the cloud computing industry are the following three: Security Assertion Markup Language (SAML), OAuth, and OpenID Connect (OIDC). 

\subsection{SAML}
Security Assertion Markup Language (SAML) and its associated protocols form an open standard for communicating information, ``packaged'' in an \emph{assertion}, about a subject, such as a user \autocite{Kemp2005}. SAML assertions, provided by an \emph{identity provider} (IdP), may represent authentication information, authorization decisions, or attributes associated with the subject. A \emph{service provider} (SP) can then use these assertions for access control and identification.

The use of SAML 2.0 can support single sign-on (SSO) for browsers, as specified by the Web Browser SSO Profile \autocite{Hughes2005}. When an unauthenticated HTTP user agent, in this case a browser, requests a secured resource from a service provider, the SP issues a SAML authentication request to be delivered to the identity provider by the user agent. The IdP identifies the subject, and issues a SAML response to be delivered back to the service provider by the user agent. The service provider can then establish a security context for the subject and return the requested resource. 

\subsection{OAuth}
``The OAuth 2.0 authorization framework enables a third-party
application to obtain limited access to an HTTP service, either on
behalf of a resource owner [...], or [...] on its own behalf'' \autocite{Hardt2023}.

A typical OAuth flow consists of a \emph{client} (e.g. an application) requesting authorization from a \emph{resource owner}. When the resource owner issues an \emph{authorization grant} to the client, it may then exchange that authorization grant for an \emph{access token} from an authorization server. Using that access token, it may then access a protected resource, owned by the resource owner, on the resource server. \autocite{Hardt2023}

JSON Web Tokens (JWTs) may be used both as OAuth 2.0 authentication grants and tokens \autocite{Jones2015a, Bertocci2021}. They provide a secure way to communicate information (referred to as claims) about a subject, encoded as a JSON object which may be signed and/or encrypted. \autocite{Jones2015}

\subsection{OpenID Connect}
As detailed by its specification, OpenID Connect (OIDC) is ``a simple identity layer on top of the OAuth 2.0 protocol''. Information about the end user is conveyed in claims, as part of a JWT called the ID token. This information can then be used by a client to authenticate the user. \autocite{Sakimura2014} 

\subsection{Time-Based One-Time Passwords}
A Time-based One-Time Password (TOTP) is a numeric code valid during only a specific time window, designed for use in two-factor authentication flows \autocite{MRaihi2011}. One known implementor of the algorithm, the Google Authenticator app, generates 6-digit codes valid for 30 seconds each \autocite{GoogleKeyUri}.

The TOTP algorithm is an extension to the HMAC-based One-Time Password (HOTP) algorithm, which generates a code based on a shared secret and an integer counter value. For the counter value, TOTP uses the current UNIX time (time passed since midnight UTC on 1 January 1970), divided by a time step. For example, with a time step of 30 seconds, the counter value will the current UNIX time in seconds, divided by 30. This means the counter value will be the same during this 30 second time window, resulting in an identical TOTP code when provided with the same secret key. Verifying a received code requires the validator to generate its own code using the user’s shared secret, and checking whether they match.

The underlying HOTP algorithm generates its resulting \(n\)-digit code in a series of steps \autocite{MRaihi2005}. First, it creates an HMAC hash of a 64-bit counter value using a shared secret. The resulting hash is then truncated to 31 bits using a bitwise operation called dynamic truncation, illustrated in listing~\ref{lst:DT}. This 31-bit binary array is then converted to a numeric value, of which the least significant \(n\) digits are used to form an \(n\)-digit code.

\begin{listing}[h]
\begin{minted}{text}
DT(String) // String = String[0]...String[19]
  Let OffsetBits be the low-order 4 bits of String[19]
  Offset = StToNum(OffsetBits) // 0 <= OffSet <= 15
  Let P = String[OffSet]...String[OffSet+3]
  Return the Last 31 bits of P
\end{minted}
    \caption[Dynamic Truncation algorithm]{Dynamic Truncation algorithm \autocite{MRaihi2005}\label{lst:DT}}
\end{listing}

Google Authenticator uses a time step of 30 seconds, a code length of 6 digits, HMAC-SHA1 for its TOTP implementation, and expects the secret key to be base32-encoded \autocite{GoogleKeyUri}.

To implement a Google Authenticator compatible TOTP validator in a specific language, it will need to be capable of retrieving the current UNIX time, decoding a base32 string, generating an HMAC-SHA1 hash, and performing operations on an array of bits. Though this may be possible in most languages, some could be better suited to this than others.

\section{Server-side languages}
\subsection{Language characteristics}
Before discussing individual programming languages, this section will take a closer look at certain characteristics. Important findings here may later be used in the requirements analysis, and will help in discussing programming languages one by one later on.
\subsubsection{Memory Safety}
As defined by the \textcite{Prossimo2021}, memory safety is “a property of some programming languages that prevents programmers from introducing certain types of bugs related to how memory is used.” An example of a bug like this is an out of bounds read or write, such as retrieving or writing the 11th item in a list of 10 items. This operates on data stored outside of the list's bounds, and thus accesses memory that is not meant to be accessed through there. Another vulnerability scenario, use after free, happens when memory is accessed after the program has freed it, which may contain other data by then.

These memory safety bugs are often at the root of security vulnerabilities, as can be seen in the CWE list of top 10 known exploited vulnerabilities \autocite{CWE2023}. Four out of ten entries in this list are related to memory safety, specifically stating C and C++ as languages prone to these vulnerabilities.

Their danger is also highlighted by reports from industry giants like Google and Microsoft. Microsoft has reported that memory safety issues are at the root of 70\% of their security vulnerabilities \autocite{Thomas2021}. Google reported similar numbers, with memory safety being the cause of 59\% of high severity security vulnerabilities in Android, and around 70\% in Chromium \autocite{ChromiumSecurity,Deus2021}.

In February 2024, the White House published a report outlining guidelines to improve software security and its measurability, with a section specifically dedicated to memory safety in programming languages \autocite{NationalCyberDirector2024}. The report highlights the severe security impact of memory safety vulnerabilities, and calls for the use of memory safe languages. This follows an earlier report authored by multiple international government agencies which also warns against the danger of memory safety vulnerability, and champions the use of memory safe languages \autocite{CISA2023}.

\subsubsection{Type systems}
Programming languages can be categorized into two groups depending on their type system. In a statically-typed language, data types of variables are determined at compile time, whereas in a dynamically-typed language, these are assigned at runtime \autocite{MDNStaticTyping,MDNDynamicTyping}. When a variable is used incorrectly (e.g. a non-existent property is accessed on an object or an integer is being multiplied by a string), a type-checked program will return a type error. In a dynamically-typed language this would happen at runtime, but a statically typed language could catch this at compile time. This way, the static type checker prevents invalid programs from compiling. It may, however, also prevent some valid programs from compiling \autocite{Mitchell1990}. The programmer could know the program is correct, but the type system might not.

Static typing does bring some valuable benefits with it however: \textcite{Gao2017} evaluated how well TypeScript and Flow, statically typed supersets of JavaScript, were able to catch bugs in public JavaScript projects. Despite this research only applying to bugs which had already made it past testing and review, they found that TypeScript and Flow were able to detect 15\% of bugs. This demonstrates that static type checking is a valuable tool for preventing bugs before they can make it to production.

Another study by \textcite{Zhang2021} analyzed bug resolution data from popular GitHub projects and ``found evidence for a lower elapsed resolution time for bug resolution committed to projects constructed from statically typed languages''. This shows that in addition to preventing a significant proportion of bugs, static type systems may also help resolve them more quickly.

Finally, \textcite{Endrikat2014} found that ``static type systems [act] as a form of implicit documentation'', with this effect being even more apparent with explicit documentation. On the other hand, the benefits of dynamically typed languages were not as strongly strengthened by explicit documentation. 


\subsubsection{Summary}
Considering the cybersecurity space in which TrustBuilder operates, existing literature provides clear guidance for selecting certain programming languages by their characteristics. 

Memory unsafe languages such as C and C++ are widely panned for their detrimental impact on the security of applications, making them decisively unfit for this use case. 

Statically typed languages exhibit compelling characteristics which can help make software more robust by raising type errors at compile time instead of at runtime. They help prevent bugs, help resolve bugs more quickly, and serve as valuable documentation even in addition to explicit documentation. These are all qualities which would be of significant value in a customer-facing security product.

\subsubsection{JavaScript and TypeScript}
In both surveys, JavaScript proves to be the most widely used programming language across developers. Despite having originally been created for usage in browsers \autocite{NCC1995}, it can also be used in server-side environments on runtime systems such as Node.js \autocite{OpenJSFoundation}.

According to the TypeScript Handbook, TypeScript is a typed superset of JavaScript \autocite{TypeScript2023}. It is designed to mitigate type-related bugs JavaScript programs are prone to by statically analyzing the code and providing meaningful errors at compile-time instead of at runtime. After checking code for type errors, the compiler produces plain JavaScript code. This allows the compiled code to be run in any JS runtime environment.

\subsubsection{Python}
Python is a general-purpose programming language designed with simplicity and readability in mind \autocite{Peters2004}. Based on GitHub's 2022 Octoverse report, \textcite{Scarlett2023} states that Python is commonly used for web and software development, task automation, machine learning and data science, financial analysis, and artificial intelligence.

The official Python documentation describes it as being ``suitable as an extension language for customizable applications'' \autocite{PSF2023}.

\subsubsection{Java}
Java is a general-purpose object-oriented programming language \autocite{Lindholm2015}. A Java application may be compiled to instructions for the Java Virtual Machine (JVM), which allows the language to be hardware- and operating system-independent. Other popular JVM languages include Kotlin and Scala \autocite{StackOverflow2023, JetBrains2023}.

\subsubsection{WebAssembly}
As stated on its home page, ``WebAssembly (abbreviated Wasm) is a binary instruction format [...] designed as a portable compilation target for programming languages, enabling deployment on the web for client and server applications'' \autocite{WebAssembly}. Although it is not a programming language itself, a runtime environment that can run Wasm applications would be able to run applications written in a variety of languages, such as C, C++, and Rust \autocite{EmscriptenContributors2015, RWWG2023}.

\section{Software Supply Chain Security}
Software supply chain vulnerabilities make up two entries in the OWASP Top 10, a document listing some the most critical security risks for web applications: Vulnerable and outdated components, and software and data integrity failures \autocite{OWASPTop102021}. While these factors are not directly tied to programming languages themselves, their ecosystem and its availability of necessary tooling does influence how straightforward it is to mitigate these risks.

\subsection{Software Bill Of Materials}
One way to mitigate these risks is a software bill of materials, or SBOM for short. It is a document detailing all dependencies, including transitive ones, used in a piece of software \autocite{SBOM2024}. Using these, software authors and consumers are able to identify vulnerable components and monitor their security. Other tools can then scan these SBOMs to generate a list of known vulnerabilities in the used versions of components and suggest mitigations such as upgrading to patched versions. 
According to GitLab's Sandra \textcite{Gittlen2024}, the two most popular SBOM standards at this time are SPDX and CycloneDX.

SPDX is an SBOM standard developed by the Linux Foundation, and first released in 2011 \autocite{SPDXAbout}. In 2021, SPDX specification 2.2.1 was recognized as an ISO standard.
The SPDX community provides Gradle and Maven plugins to generate SBOMs in the SPDX format \autocite{SPDXTools}.

CycloneDX is another SBOM standard, backed by the OWASP foundation, initially developed for use with its Dependency-Track software \autocite{CycloneDXHistory}. The project provides first-party tools to generate CycloneDX SBOMs for Java, Kotlin, Python, PHP, C\#, Go, JavaScript, TypeScript and Rust projects \autocite{CDXTools2024}.

Third-party services such as GitHub, GitLab, and Snyk are also capable of generating SBOMs for projects in a variety of languages \autocite{GitHubSBOM,Gittlen2024,Snyk2024}. GitHub generates them in the SPDX format, GitLab in the CycloneDX format, and Snyk is capable of both.

\section{Current approach}
TrustBuilder's current technology for allowing customization and extension of their platform are called workflows \autocite{DefiningWorkflows}. Workflows consist of elements, such as conditions, scripts, and adapters, which are executed in an order defined by their connections. Custom code can be written in the form of JavaScript functions, which can be executed by script elements. Java code can also be uploaded as a ``service'' JAR file to the workflow platform, which can then be called from within a JavaScript function.

\section{Comparable services}
\subsection{Auth0 Actions}
Auth0 is an IAM platform that enables developers to add authentication and authorization services to their applications \autocite{Auth0Overview}. Actions, one of their customization capabilities, let customers ``customize and extend Auth0's capabilities with custom logic'' \autocite{Auth0Actions}. Auth0 Actions are independent Node.js JavaScript functions which can be executed at specific points in identity flows. These functions typically take two parameters as input: an event object and an API object \autocite{Auth0Triggers}. The event object describes an interaction with the platform. The API object provides the function implementation with the ability to determine the outcome of the flow, or call other Auth0 APIs relevant to the flow. These function are also able to use dependencies from the npm package registry.


\subsection{Cloudflare Workers}
A more general-purpose example, Cloudflare Workers, announced by Kenton \textcite{Varda2017}, were created to allow customers to run code on Cloudflare's edge network, to cover use cases Cloudflare themselves can't. A Cloudflare Worker could initially only be written in JavaScript, but can now run code written in any language that compiles to JavaScript (such as TypeScript, Python, and Kotlin) or WebAssembly (such as C, C++, Rust and Go). \autocite{Varda2018, Koeninger2020}

\subsection{GitHub Actions}
GitHub Actions, GitHub's CI/CD platform, allows for the execution of logic when certain events take place within a GitHub repository \autocite{GitHubActions}. Although this is aimed more at DevOps workflows, it serves as another example of platforms providing extensibility and customizability for their clients. An Actions workflow consists of ``jobs'', which contain a series of steps. These steps can either be shell scripts or actions. Actions are reusable units of logic, and can be created by any user \autocite{GitHubCustomActions}. There are three types of actions:
\begin{itemize}
    \item{JavaScript actions} 
    \item{Docker container actions, allowing more freedom in terms of operating systems, tools and language choice.}
    \item{Composite Actions, consisting of multiple workflow steps}
\end{itemize}
Actions take input parameters as environment variables, and provide outputs by setting environment variables.
